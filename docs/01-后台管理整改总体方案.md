# Shopro AI 厂商运营后台整改总体方案

> 文档版本：V1.0  
> 编制日期：2026-08-20  
> 适用仓库：`Shopro-backend`  
> 当前基线：Vue 3 + TypeScript + Element Plus + Axios + MSW + localStorage 的前端演示工程

## 1. 文档目的

本文档用于指导 Shopro AI 厂商运营后台从“页面型 Demo”整改为“能够演示真实运营闭环、并可平滑接入真实后端”的运营控制台。

本文档解决三个问题：

1. 当前六个后台模块应保留、重构或新增哪些能力。
2. 在不立即接入 Spring Boot、数据库、支付和 AI 服务的前提下，如何先把业务模型和交互逻辑整改正确。
3. 后续 AI 或研发人员应按照什么顺序实施，避免只修改界面而破坏数据一致性。

配套文档：

- `docs/02-后台管理目标数据模型与接口规范.md`
- `docs/03-后台管理AI整改执行任务书.md`

## 2. 参考基线

本方案以以下资料和当前源码为基线：

## 3. 当前版本判断

当前项目已经具备稳定的演示基础：

- 页面不直接读取 Mock 数据，统一通过 `/api/admin/**` 请求。
- MSW 可以模拟用户启停、积分调整、任务重试、内容审核和日志记录。
- 演示数据可以在浏览器刷新后保留，并可以一键重置。
- 技术栈轻量，适合继续快速迭代。

但当前只能称为“基础管理操作 Demo”，还不能称为完整运营闭环，主要原因如下：

| 问题 | 当前表现 | 业务后果 |
| --- | --- | --- |
| 数据对象互不关联 | 用户、任务、内容、订单分别生成 | 无法从投诉追查到任务、扣费和订单 |
| 余额直接修改 | 输入正负数后覆盖用户积分 | 无流水、无原因、无法审计和对账 |
| 任务原地重试 | 失败任务直接变为运行中和成功 | 丢失失败尝试、重复成本和扣费依据 |
| 内容状态混用 | 一组状态同时表达审核和上下架 | 私有内容、公开内容和发布状态边界错误 |
| 订单只读 | 订单没有支付事件、权益到账和退款 | 无法处理支付成功未到账等真实问题 |
| 总览部分写死 | 营收、趋势、订单指标与业务数据无关 | 页面操作后统计不一致 |
| 单一超级管理员 | 所有操作没有角色和审批边界 | 高风险动作无法限制和追责 |
| Mock 过度集中 | 类型、API、种子和处理器集中在单文件 | 后续 AI 容易产生大范围回归 |

当前 `pnpm build` 可以通过，但构建结果提示多个 JavaScript chunk 超过 500 kB。主要原因包括全量注册 Element Plus、Dashboard 使用 `import * as echarts` 以及图表依赖进入较大的异步 chunk。该问题不阻塞业务整改，但应在功能闭环稳定后单独优化，避免与领域重构混在同一阶段。

## 4. 整改目标和非目标

### 4.1 本轮整改目标

1. 保留当前 Vue 3、Element Plus、Axios、MSW 技术栈。
2. 将后台从“列表增删改查”改成“异常发现—定位—处理—通知—审计”的运营闭环。
3. 建立用户、组织、工单、工作流、任务执行、内容风险、订单、支付和积分流水之间的关联。
4. 所有 Dashboard 和统计数据从同一套 Mock 数据实时计算。
5. 形成稳定的目标 API 契约，为未来 Spring Boot 接入提供依据。
6. 保留 Demo 模式和演示数据重置，但通过环境模式与生产能力隔离。
7. 每个阶段都必须可以独立构建和演示。

### 4.2 本轮非目标

除非用户另行明确要求，本轮整改文档不要求后续 AI 立即完成以下内容：

- 创建或接入真实 Spring Boot 服务。
- 连接真实数据库、支付渠道或 AI 模型。
- 实现真实短信、邮件或第三方平台通知。
- 实现完整财务会计系统或法务合规系统。
- 将 Shopro 用户端 42 个页面全部复制到运营后台。
- 替换现有 Vue 技术栈或引入大型后台模板。

## 5. 目标产品定位

整改后的后台定位为：

> Shopro AI 平台侧的 AI 内容生产履约、客户服务、风险治理和交易计费控制台。

后台管理的重点不是管理前台的所有页面，而是保障以下四条链路：

1. AI 任务是否成功、是否按时交付、失败是否退回积分。
2. 用户支付、套餐权益、积分入账和退款是否一致。
3. 对外发布和公共内容是否经过必要的风险治理。
4. 每一次人工操作是否有原因、权限、关联业务和审计记录。

## 6. 目标角色

Demo 阶段可以通过角色切换模拟权限；真实生产环境由服务端强制校验。

| 角色 | 主要职责 | 关键权限 |
| --- | --- | --- |
| `CUSTOMER_SERVICE` | 用户查询、客诉处理 | 查看用户全景、创建工单、发起补偿申请 |
| `AI_OPERATOR` | AI 任务异常处理 | 查看工作流、重试、申请取消、切换处理策略 |
| `RISK_REVIEWER` | 内容风险复核 | 查看风险详情、通过、驳回、处理申诉 |
| `FINANCE` | 订单、退款、对账 | 查看支付事件、审核退款、处理到账异常 |
| `OPERATION_MANAGER` | 运营配置和审批 | 用户能力限制、补偿审批、公告配置 |
| `AUDITOR` | 审计检查 | 只读查看敏感操作和变更前后数据 |
| `SUPER_ADMIN` | 系统治理 | 管理员、角色、系统级配置 |

## 7. 目标信息架构

为控制改造范围，仍保留六个一级菜单，但调整名称和职责。

| 一级菜单 | 建议路由 | 子页面 | 核心职责 |
| --- | --- | --- | --- |
| 运营工作台 | `/dashboard` | 工作台 | 个人待办、业务异常、AI 履约、经营和风险概览 |
| 客户中心 | `/customers` | 用户、企业、工单、用户详情 | 查询客户、处理账号、积分和客诉 |
| AI 生产运营 | `/ai-operations` | 工作流、任务详情、供应商概览 | 处理生成失败、超时、取消、重试和成本异常 |
| 风险与内容 | `/risk` | 风险事件、审核详情、申诉、公共内容 | 只审核命中风险或需要公开/发布的内容 |
| 交易与计费 | `/billing` | 订单、退款、积分流水、套餐 | 处理支付、权益发放、退款和计费一致性 |
| 系统治理 | `/system` | 服务概况、管理员、审批、审计日志 | 权限、审计、敏感操作审批和业务影响告警 |

为减少一次性路由重构风险，第一阶段允许保留 `/users`、`/jobs`、`/contents`、`/orders` 旧路径，并通过重定向或路由别名迁移到新结构。

## 8. 页面级整改要求

### 8.1 运营工作台

页面第一屏应优先展示“可行动信息”，而不是累计数字。

必须包含：

- 我的待办：异常任务、未退积分、支付未到账、待复核风险、待审批退款、未关闭工单。
- AI 履约：首次成功率、重试后成功率、队列长度、超时任务、P95 生成时长。
- 经营数据：付费用户、现金实收、退款、积分消耗、供应商成本、预估毛利。
- 服务影响：异常能力、影响用户数、影响任务数、开始时间和降级状态。
- 所有卡片和待办必须可点击并跳转到带筛选条件的目标页面。

不得继续保留与业务种子无关的硬编码营收、趋势和订单指标。

### 8.2 客户中心

用户列表必须支持用户 ID、姓名、邮箱、企业、套餐、状态、风险等级和日期筛选。

用户详情至少包含：

- 基本信息和所属企业。
- 当前套餐和能力状态。
- 积分余额及积分流水。
- 历史订单和退款。
- AI 工作流和失败任务。
- 内容风险记录。
- 工单、补偿和后台操作记录。

账号状态从单一启用/禁用拆为能力状态：登录、生成、发布、API。每次限制必须填写原因、有效期、是否通知用户和关联工单。

积分调整必须创建流水，不得直接覆盖余额。流水必须记录变动类型、原因、关联业务、调整前后余额和操作人。

### 8.3 AI 生产运营

业务模型必须从单条任务升级为：

```text
工作流 Workflow
  └─ 子任务 Job
      └─ 执行尝试 JobAttempt
```

工作流代表用户发起的一次完整生成；子任务代表脚本、翻译、配音、封面、视频、合成或发布；执行尝试代表某个任务的每次真实请求。

重试必须新增 `JobAttempt`，不得覆盖旧失败记录。任务详情必须展示供应商、模型、第三方任务号、错误分类、耗时、重试记录、供应商成本、积分扣退和输出预览。

### 8.4 风险与内容

私有内容不进入全量人工审核。只有以下情况创建风险事件：

- 自动安全检测命中。
- 准备公开或对外发布且需要复核。
- 被举报、被第三方平台驳回或用户提出申诉。
- 数字人、声音克隆等授权证明存疑。

必须分别维护：

- 安全审核状态。
- 内容可见范围。
- 第三方发布状态。

审核决定必须填写原因码、内部备注和面向用户的说明，并保留完整时间线。

### 8.5 交易与计费

必须形成以下链路：

```text
订单 → 支付事件 → 套餐权益/积分入账 → 任务消耗 → 失败退回 → 退款/回收
```

不得提供“人工将订单改为已支付”的按钮。支付状态只能由模拟支付事件或未来支付渠道回调推进。

套餐修改必须版本化，不能改变历史已售订单的套餐快照。

### 8.6 系统治理

服务健康要展示业务影响，而不仅是响应延迟。审计日志必须包含操作对象、变更前后、原因、关联业务、Trace ID 和结果。

Demo 数据重置必须满足：

- 仅当 `VITE_APP_MODE=demo` 时显示入口并注册 Mock 接口。
- 重置前明确提示会删除哪些本地演示数据。
- 生产环境不显示入口，也不暴露 `/api/admin/demo/reset`。

## 9. 必须补充的横向能力

### 9.1 全局搜索

支持用户 ID、邮箱、企业、订单号、支付交易号、工作流 ID、任务 ID、供应商任务号、内容 ID 和工单号。

### 9.2 客诉工单

工单作为人工运营行为的业务依据，可以关联用户、组织、任务、订单、内容和积分流水。补偿、退款和长期账号限制应尽量关联工单。

### 9.3 统一审计

所有敏感动作必须通过统一动作服务写入审计，包括：

- 用户能力限制和解除。
- 积分补偿、扣减和冲正。
- 任务重试、取消和人工结算。
- 内容复核、驳回和移除公开展示。
- 退款申请和审批。
- 套餐、角色和系统配置修改。

### 9.4 统一状态和错误码

页面不得自行维护中文状态映射。状态枚举、标签、颜色、允许动作和错误码统一放在 `src/constants/` 或领域模块中。

## 11. 分阶段实施路线

### 阶段 A：架构整理，不改变现有业务表现

- 拆分类型、API、Mock 数据和处理器。
- 增加统一列表参数、错误处理、状态常量和 schemaVersion。
- 保持现有六个页面功能可用。
- `pnpm build` 必须通过。

### 阶段 B：客户和积分闭环

- 增加用户详情、企业、工单和积分流水。
- 取消直接修改余额。
- 所有调整写入流水和审计。

### 阶段 C：AI 工作流闭环

- 增加 Workflow、Job、JobAttempt。
- 重试新增执行尝试。
- 打通任务、积分扣退、成本和审计。

### 阶段 D：风险治理闭环

- 将 Content 审核迁移为 RiskEvent。
- 分离安全、可见性和发布状态。
- 增加详情预览、理由和申诉。

### 阶段 E：交易计费闭环

- 增加订单详情、支付事件、权益发放、退款和套餐版本。
- 处理支付成功未到账和重复回调演示场景。

### 阶段 F：工作台和系统治理

- 基于前述真实数据计算 Dashboard。
- 增加全局搜索、角色、权限、审批和完整审计。
- 完成四条端到端验收场景。

### 阶段 F2：前端质量和包体优化

- 将 ECharts 改为按需注册折线图、饼图、组件和渲染器。
- 评估 Element Plus 按需导入，避免一次性全量注册全部组件。
- 保持路由级懒加载，并根据构建报告调整 vendor 分包。
- 处理图表实例销毁和窗口尺寸变化，避免重复进入页面造成内存泄漏。
- 优化前后对比构建产物，不以简单调大 `chunkSizeWarningLimit` 代替真实优化。

### 阶段 G：真实后端接入，单独立项

- 根据配套接口规范实现 Spring Boot。
- 将前端 `VITE_USE_MOCK=false` 指向真实 API。
- 不允许页面绕过 API 层直接适配后端字段。

## 12. 整改完成定义

前端 Demo 整改完成必须同时满足：

1. 用户、任务、订单、风险、积分和工单之间存在可追踪关联。
2. 所有 Dashboard 数据来自同一套 Mock 数据动态计算。
3. 余额由积分流水推导或由事务规则同步维护，不能随意覆盖。
4. 任务重试保留旧执行历史且不会重复扣用户积分。
5. 私有内容不会默认进入人工审核。
6. 订单支付状态不允许被运营直接修改。
7. 所有敏感操作都有原因、操作人、业务关联和审计记录。
8. Demo 重置仅在 Demo 模式可见。
9. 列表具备加载、空、错误、分页、筛选和重置状态。
10. `pnpm build` 通过，无 TypeScript 错误。
11. 四条端到端验收场景全部通过。

## 13. 必须在实施前确认的产品口径

如未获得用户新的决定，后续 AI 按以下默认口径实施：

1. 计费模式：套餐订阅/购买与积分消耗并存。
2. 内容范围：用户内容默认私有；公开展示和对外发布才触发更严格治理。
3. 失败扣费：最终失败原则上自动退回用户积分；供应商已产生的成本由平台承担。
4. 任务重试：系统自动处理可重试异常，人工只处理多次失败或特殊业务问题。
5. Demo 目标：先在 Mock 环境完整演示真实业务规则，不伪装成已经接入真实后端。
