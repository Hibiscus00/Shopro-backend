# Shopro AI 后台目标数据模型与接口规范

> 文档版本：V1.0  
> 编制日期：2026-08-20  
> 用途：作为前端类型、MSW Mock、未来 Spring Boot DTO 和接口联调的共同契约

## 1. 设计原则

1. 所有核心对象使用稳定 ID 关联，禁止以用户名、标题等展示字段建立关系。
2. 金额统一使用最小货币单位整数，例如人民币分；禁止使用浮点数存储金额。
3. 积分使用整数，余额变更必须产生流水。
4. 日期时间统一使用 ISO 8601 字符串，Mock 中也不得继续使用本地化字符串作为数据值。
5. 执行状态、审核状态、可见性和支付状态必须使用独立枚举，禁止复用一个通用 `Status`。
6. 任务重试生成新的执行尝试，订单回调生成新的支付事件，积分调整生成新的流水。
7. 所有敏感写操作携带 `reason`、`operatorId` 或从当前会话解析操作人，并写入审计。
8. Mock 和真实后端返回同一接口结构；页面不得针对 Mock 编写特殊分支。

## 2. 通用 API 类型

```ts
export interface ApiResponse<T> {
  code: string
  message: string
  data: T
  traceId: string
}

export interface PageResult<T> {
  items: T[]
  total: number
  page: number
  pageSize: number
}

export interface ListQuery {
  page: number
  pageSize: number
  keyword?: string
  status?: string
  startAt?: string
  endAt?: string
  sortBy?: string
  sortOrder?: 'asc' | 'desc'
}

export interface ApiErrorData {
  fieldErrors?: Record<string, string>
  retryable?: boolean
  details?: Record<string, unknown>
}
```

建议响应码：

| code | 含义 |
| --- | --- |
| `OK` | 成功 |
| `VALIDATION_ERROR` | 参数错误 |
| `UNAUTHORIZED` | 未登录或会话失效 |
| `FORBIDDEN` | 无权限 |
| `NOT_FOUND` | 对象不存在 |
| `CONFLICT` | 状态冲突或重复操作 |
| `IDEMPOTENCY_CONFLICT` | 幂等键重复且请求不一致 |
| `BUSINESS_RULE_VIOLATION` | 违反业务规则 |
| `INTERNAL_ERROR` | 未分类内部错误 |

当前 `code: number` 可以在阶段 A 暂时兼容，但目标契约应迁移为稳定字符串错误码。

## 5. 积分领域

```ts
export type CreditEntryType =
  | 'PAYMENT_GRANT'
  | 'PLAN_GRANT'
  | 'PROMOTION_GRANT'
  | 'JOB_CONSUMPTION'
  | 'JOB_FAILURE_REFUND'
  | 'CUSTOMER_COMPENSATION'
  | 'REFUND_RECLAIM'
  | 'MANUAL_CORRECTION'
  | 'REVERSAL'

export interface CreditLedgerEntry {
  id: string
  userId: string
  organizationId?: string
  type: CreditEntryType
  direction: 'CREDIT' | 'DEBIT'
  amount: number
  balanceBefore: number
  balanceAfter: number
  bizType: 'ORDER' | 'WORKFLOW' | 'JOB' | 'REFUND' | 'TICKET' | 'MANUAL'
  bizId: string
  reasonCode: string
  reason: string
  idempotencyKey: string
  operatorId: string
  reversedEntryId?: string
  createdAt: string
}

export interface CreateCreditAdjustmentRequest {
  direction: 'CREDIT' | 'DEBIT'
  amount: number
  reasonCode: 'SYSTEM_INCIDENT' | 'CUSTOMER_COMPLAINT' | 'MANUAL_CORRECTION' | 'RISK_PENALTY'
  reason: string
  ticketId?: string
  bizId?: string
  idempotencyKey: string
}
```

业务规则：

- `amount` 必须为正整数，方向由 `direction` 表达，不接受正负数混用。
- `balanceAfter = balanceBefore ± amount`。
- 同一 `idempotencyKey` 只能成功创建一次。
- 默认不允许扣减后余额小于 0。
- 流水创建后不可编辑或删除，只能创建 `REVERSAL` 冲正记录。
- 大额调整进入审批；Demo 默认阈值为 1000 积分。

### 7.3 执行尝试

```ts
export type JobErrorCategory =
  | 'PROVIDER_TIMEOUT'
  | 'PROVIDER_RATE_LIMIT'
  | 'PROVIDER_UNAVAILABLE'
  | 'INVALID_INPUT'
  | 'CONTENT_BLOCKED'
  | 'INSUFFICIENT_CREDITS'
  | 'CALLBACK_MISSING'
  | 'INTERNAL_ERROR'

export interface JobAttempt {
  id: string
  jobId: string
  attemptNo: number
  status: JobStatus
  provider: string
  model: string
  providerTaskId?: string
  progress?: number
  errorCategory?: JobErrorCategory
  errorCode?: string
  errorMessage?: string
  retryable: boolean
  providerCostMinor: number
  startedAt?: string
  lastHeartbeatAt?: string
  finishedAt?: string
  outputUrl?: string
  createdAt: string
}
```

任务业务规则：

- 重试创建新的 `JobAttempt`，`attemptNo` 递增。
- 旧失败尝试保持不可变。
- 同一个 `Job` 同时只能存在一个运行中尝试。
- `INVALID_INPUT`、`CONTENT_BLOCKED`、`INSUFFICIENT_CREDITS` 不允许后台直接重试。
- 最终失败且已扣积分时自动创建 `JOB_FAILURE_REFUND` 流水。
- 运营人工重试默认不再次扣用户积分。
- 取消先进入 `CANCEL_REQUESTED`；只有供应商确认或 Mock 模拟完成后才进入 `CANCELLED`。

## 8. 内容与风险领域

```ts
export interface ContentAsset {
  id: string
  ownerUserId: string
  organizationId?: string
  type: 'PRODUCT' | 'SCRIPT' | 'IMAGE' | 'AUDIO' | 'VIDEO' | 'AVATAR' | 'VOICE_CLONE'
  title: string
  previewUrl?: string
  visibility: 'PRIVATE' | 'TEAM' | 'PUBLIC'
  safetyStatus: 'NOT_SCANNED' | 'SCANNING' | 'AUTO_PASSED' | 'AUTO_BLOCKED' | 'MANUAL_REVIEW' | 'MANUAL_PASSED' | 'MANUAL_REJECTED'
  publishStatus: 'NOT_PUBLISHED' | 'SCHEDULED' | 'PUBLISHING' | 'PUBLISHED' | 'PLATFORM_REVIEW' | 'PLATFORM_REJECTED' | 'WITHDRAWN'
  createdAt: string
  updatedAt: string
}

export interface RiskEvent {
  id: string
  contentId: string
  userId: string
  source: 'AUTO_SCAN' | 'USER_REPORT' | 'PLATFORM_REJECT' | 'MANUAL'
  riskType: 'PROHIBITED_GOODS' | 'FALSE_CLAIM' | 'COPYRIGHT' | 'PORTRAIT_RIGHTS' | 'VOICE_AUTH' | 'PERSONAL_DATA' | 'OTHER'
  severity: 'LOW' | 'MEDIUM' | 'HIGH' | 'CRITICAL'
  status: 'PENDING_REVIEW' | 'PASSED' | 'REJECTED' | 'ESCALATED' | 'APPEAL_PENDING' | 'APPEAL_PASSED' | 'APPEAL_REJECTED'
  evidence: string[]
  ruleHits: string[]
  reviewerId?: string
  decisionReasonCode?: string
  internalNote?: string
  userMessage?: string
  createdAt: string
  reviewedAt?: string
  updatedAt: string
}
```

审核决定请求必须包含：

```ts
export interface CreateRiskDecisionRequest {
  decision: 'PASS' | 'REJECT' | 'ESCALATE'
  reasonCode: string
  internalNote: string
  userMessage: string
}
```

业务规则：

- 私有内容自动通过时不创建人工待办。
- 风险事件状态不能直接驱动内容公开状态，二者通过明确业务动作联动。
- 高风险和严重风险事件不得批量通过。
- 驳回必须填写面向用户的原因。
- 申诉创建新事件或追加不可变时间线，不覆盖原审核结论。

```ts

  entitlementStatus: 'PENDING' | 'GRANTED' | 'FAILED' | 'RECLAIMED'

export interface PaymentEvent {
  id: string
  orderId: string
  type: 'PAYMENT_CREATED' | 'CALLBACK_RECEIVED' | 'PAYMENT_CONFIRMED' | 'ENTITLEMENT_GRANTED' | 'ENTITLEMENT_FAILED'
  channelEventId: string
  payloadSummary: string
  processed: boolean
  idempotencyKey: string
  createdAt: string
}

export interface RefundRequest {
  id: string
  orderId: string
  userId: string
  amountMinor: number
  status: 'PENDING_APPROVAL' | 'APPROVED' | 'PROCESSING' | 'SUCCEEDED' | 'FAILED' | 'REJECTED'
  reasonCode: string
  reason: string

  ticketId?: string
  requesterId: string
  approverId?: string
  channelRefundId?: string
  createdAt: string
  updatedAt: string
}
```

业务规则：

- 订单金额使用最小货币单位整数。
- 订单状态不允许通过通用 PATCH 任意修改。
- 支付事件按 `idempotencyKey` 幂等处理。
- 权益发放和积分入账必须与支付事件关联。
- 退款申请和退款执行分离。
- 套餐权益以订单中的 `planSnapshot` 为准，不追随套餐后续修改。

## 13. 必须内置的演示场景

种子数据不应只追求数量，必须稳定包含以下具名场景：

1. `SCENARIO_JOB_FAILED_CREDIT_NOT_REFUNDED`：视频任务供应商超时，已扣积分但自动退回失败。
2. `SCENARIO_PAYMENT_PAID_ENTITLEMENT_FAILED`：支付成功但套餐权益未发放。
3. `SCENARIO_RISK_HIGH_PENDING`：待人工复核的高风险视频。
4. `SCENARIO_APPEAL_PENDING`：用户已提交申诉，等待二次审核。
5. `SCENARIO_REFUND_PENDING_APPROVAL`：退款待财务审批。
6. `SCENARIO_PROVIDER_DEGRADED`：视频模型服务降级并影响多条任务。
7. `SCENARIO_ENTERPRISE_CUSTOMER`：包含企业、管理员、成员、套餐和 API 能力的客户。

随机数据可以用于填充列表，但所有端到端演示必须依赖固定场景 ID，确保每次重置后可复现。

## 14. 旧接口迁移策略

| 旧接口 | 目标处理 |
| --- | --- |
| `GET /admin/users` | 第一阶段兼容，最终迁移到 `/admin/customers/users` |
| `PATCH /admin/users/:id/status` | 废弃，改为能力状态接口 |
| `POST /admin/users/:id/credits` | 废弃，改为积分调整流水接口 |
| `GET /admin/jobs` | 第一阶段兼容，最终以 Workflow 为主列表 |
| `POST /admin/jobs/:id/retry` | 保留动作含义，但返回新 `JobAttempt` 和更新后的 Job |
| `PATCH /admin/contents/:id/review` | 废弃，改为风险事件审核决定 |
| `GET /admin/orders` | 第一阶段兼容，最终迁移到 `/admin/billing/orders` |
| `GET /admin/audit-logs` | 迁移到 `/admin/system/audit-logs` |

迁移期间不得同时维护两套不同业务规则。旧接口只能调用新领域服务或 Mock 规则的兼容适配器。
